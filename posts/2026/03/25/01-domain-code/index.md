# 小さく始めるドメインの匂いがするコード

みなさんClean Architectureは好きですか？ 僕は嫌いです。

いい加減に物申そうと思って、最近ちゃんと『Clean Architecture 達人に学ぶソフトウェアの構造と設計』を読みました。多くの人が言っているように、この本の本質は、同心円の図ではなく、ましてディレクトリ構成でもありません。というわけで、多くの人が雑に語る「Clean Architectureやってみた」という話がめちゃくちゃ嫌いです。

僕の解釈では、この本の本質は

1. 仮想メソッド（インターフェイス）を活用すれば、依存性を逆転することができる
2. コアとなるドメインロジック以外をプラガブルにすることで、変更容易性が高く保守しやすくなった経験がある

というところだったと思います。全体を通して、仮想メソッドをがちゃがちゃやってきたぜ、という昔語りというのがClean Architectureの全体像でしたね。

で、で、です。実務のコードを見渡すと、まぁ基本、トランザクションスクリプトでぐちゃぐちゃしたコードが大量にあるか、あるいはClean Architectureを導入したと言っているが別に物事は楽になっていない、のどちらかがほとんどではないでしょうか。

この記事では、最近僕が試して腑に落ちた、ドメインの匂いがするコードを書くコツを記しておきます。

## ドメインの匂いがするコードってなんだ

あなたのプロダクトにおける「ビジネスロジック」ってなんですか？ よくわからないですよね。日本語における「ビジネス」ってお金儲けみたいな意味合いですし。

それはともかく、ビジネスロジックは、製品仕様を満たすためのルールとワークフローのことを指します。ドメインの匂いがするコードとは、**ルールやワークフローが、プログラマ以外にも理解できるような分割・命名できている状態**を指します。DDDではユビキタス言語と呼ばれるやつです。

ドメインの匂いがするコードは、仕様の把握がしやすく、関係者との共通認識が取りやすいです。ロジックをすべて探索しなくても命名から予想が付くし、プログラマ以外の人とも同じ用語で会話できますからね。

このメリットは、初期実装よりも保守のフェーズで特に効いてきます。いわゆる変更容易性です。

変更容易性とは、安心して変更を加える（新しい仕様にモデリングし直す）ことができることです（少ないコードで変更できることではないよ！）。変更容易性を高めるには、現状の仕様を把握しやすいこと、十分にテストされていることが求められます。仕様が明確で十分にテストされていれば、変更を加えたときに、壊れていないことを確認することが容易になります。

つまり、**ドメインの匂いがするコードとは、コードがルールを表しており、変更容易性が高い**ということです。

この状態を維持するために、いわゆるEvansのDDDではEntityやValue Objectといった概念が導入されました。『関数型ドメインモデリング ドメイン駆動設計とF#でソフトウェアの複雑さに立ち向かおう』（以下、WlaschinのDDD）では、ルール上存在できない状態を表現できないように型を作ることが提案されました。いずれもルールをコードに表すための道具にすぎないことを忘れてはいけません。

## 結局、Clean Architectureってなんだ

ここまでドメインの匂いがするコードについて説明してきましたが、ルールとワークフローの話しかしていません。実際にプロダクトを作るには、UIがあったり、データを永続化したりする必要があります。Clean ArchitectureはビジネスロジックとUIや永続とを結合するためのベストプラクティスを示しています。

Clean Architectureでは、ビジネスロジック（著書では「方針 (policy)」と呼ばれている）以外は「詳細 (detail)」であり、その決定は延期できるべきだと主張しています。詳細の決定を延期することで、非機能要件の把握や実験に時間を使うことができます。詳細をプラガブルにすることで、詳細の決定に関わらず開発を行うことができ、詳細の変更（著書ではパンチカードから磁気テープに移行した例があった）に強くなります。

とまぁ、これはBobおじさんの昔話ですが、個人的には詳細を切り離すことのメリットはテスタビリティにあると考えています。一番重要な、そのプロダクトならではのロジックがテストしにくいと、品質がボロボロになっていきます。これを避けるためにも、まずルールがテストされていることが重要です。逆に詳細側のテスト（外部サービスとの通信とか）なんて、書いても大体モック自体をテストすることになりがちなので、あんまり価値がないということは、みなさんも経験あると思います。

じゃあビジネスロジックと詳細の結合部分をどうするんだ？という問題に対する、一般解として提案されたのが、例の同心円図「The Clean Architecture」です。

基本ルールは次の2点です。

1. 依存関係は一方通行で、 詳細 → ワークフロー → ルール とする
2. 逆方向への依存はインターフェイスを通じて依存性を逆転する

この思想を実践することにより、ルールは純粋なコードになり、ワークフローは詳細の差し替えが容易になるので、ビジネスロジックはどこにデプロイするにも困らないし、テストするのも容易になります。

ドメインの匂いのするコードを実践しようとしたとき、どうやってインフラと結合するんだということが問題になります。Clean Architectureの最大の主張である依存性の逆転に従い、ビジネスロジックはインターフェイスのみに依存することで、テスタブルで変更容易性が高い状態を維持することができます。

## 戦術的DDDもClean Architectureもうまくいかない理由

DDDやClean Architectureを導入しても、コードの置き場所に悩んだりボイラープレートが増えたりするばかりで、見通しが良くなったりドメインの匂いがぷんぷんしないことが多いでしょう。この原因は、解こうとしている問題が小さすぎるか、大きすぎることにあります。

### 問題が小さすぎる

FizzBuzz Enterprise Editionと揶揄されるやつですね。ドメインのルールがほとんどない、簡単なCRUDだけのアプリケーションには重厚なアーキテクチャは必要ありません。ただのオーバーエンジニアリングです。

### 問題が大きすぎる

トップレベルのディレクトリ構成だけでClean Architectureを導入したとか言ってませんか？ 例えばトップレベルに entities と usecases ディレクトリを作りました。すると、問題を分析する前に、DBのテーブルと同じ名前のエンティティを作成して……と開発が進んでいきます。その結果、エンティティがDBと同じ形式になり、責務過多なUserやOrderができあがっていきます。

何が悪かったのでしょうか？ 原因は「戦術的」といってモデリングをスキップしたことにあります。本来ならば境界づけられたコンテキストを特定し、問題を分割するところから始まるはずでした。それをスキップしたため、大きく複雑な問題を、複雑なまま解こうとしてしまいました。また、ドメインモデルがDB（つまり詳細）の設計に引っ張られて、ルールの匂いが出せなくなってしまいました。

このことから導けるアプローチはこうです:

1. 複雑な問題に絞って、問題（ドメイン）を分割する
2. 解こうとしている問題に合った側面から見たルールを記述したエンティティを作る

## 小さく始めよう

アーキテクチャを学ぶと全体をいい感じにすることばかり考えてしまいますが、現実の問題に当てはめると、簡単な問題もあれば複雑な問題もあります。新規で書くものもあれば、既存のコードのリファクタリングもあります。いずれにしても、複雑な問題にぶつかったときに、小さく始めて学習しながら開発を進めていくことが大事です。

### ワークフローから始める

WlaschinのDDDにおけるワークフロー、Clean Architectureにおけるユースケースから、ドメインの匂いのするコードを書き始めましょう。おすすめの考え方は、WlaschinのDDDで示されているように、書類の変換としてモデリングすることです。

> 典型的なビジネスプロセスは、データやドキュメントの変換の連続だと考えられます。ビジネスの価値は、この変換の過程で生み出されるため、これらの変換がどのように機能し、互いにどのように関係しているかを理解することが非常に重要です。

『関数型ドメインモデリング』から具体例を引用します。受注という業務について分析を行ったところ、まず注文書を受けたら、お客様の情報と製品が有効かをチェックし、書類にチェックマークをつけます。次に製品カタログを見て金額を計算し、合計金額を記入します。この注文書を2部コピーして、お客様に確認書と一緒に返信し、配送・請求部門に回します。

この業務を書類の変換としてモデリングすると、「未検証の注文書」を受け取り、検証して「検証済みの注文」を得て、価格を計算して「価格計算済みの注文」を得て、他のコンテキストに送信する、というワークフローを得ることができました。

このように書類の変換としてモデリングすると、書類ごとに満たすべき条件が明らかになります。これがルールですね。このルールを、WlaschinはF#の強力な型システムを利用して表現することを主張していますが、他の言語でもエンティティ・値オブジェクトによって表現できるでしょう。そうです、エンティティとはDBのテーブルではなく、業務を書類の変換と捉えたときの書類のルールを表すものだと考えれば良いのです。

戦術的にやるならば、わざわざイベントストーミングをしなくても、複雑な問題の分割方法として利用することができます。ひとつの大きなワークフローを複数にステップに分け、ステップ間の入出力を書類に見立てて変換ロジックを考えてみましょう。これにより、複雑で絡み合った仕様を生む前に、ステップや中間書類に名前をつけることができ、コミュニケーションもスムーズになるはずです。

### どうやって永続化するか

WlaschinのDDDでは、データの読み書きは最初と最後にすることが勧められています。これは、純粋な書類変換ロジックができるだけ詳細に依存しないようにするためです（どうしても詳細に依存する場合は依存性を逆転すればOK）。このやり方に従うと、最初に必要な領域のデータを取得し、最後に書類の変換結果を使ってデータを書き込みます。

さて、アーキテクチャの話では大抵、ドメインはこう書きます、あとはDBはRepositoryでよろ、とだけ書かれていて、結局誰もベストプラクティスを知らずにトランザクションスクリプトを書いていますね。ここでは2つのやり方を提案しておくので、言語やワークフローの特性に合わせて使い分けてください。

#### 選択肢1: イベントを永続化する



1. 関数型のやり方: Wlaschinの例で挙げられていたように、ワークフローの出力をイベントとします。このイベントを受けてどう永続化するかを、インフラ層に実装します。
2. Unit of Workのやり方: 集約をワークフローの入力とし、処理を適用した結果の集約をワークフローの出力とします。

この考え方はEvansのDDDで集約と呼ばれるものに近いです。集約とは整合性を保つ単位です。データストアに依存して考えるものではないですが、ひとつの集約をどこかに保存するならば、1トランザクションで保存することになる、そんな単位です。ひとつのワークフローから始めるならば、そのワークフローが操作する集約からドメインモデルを設計することができます。

DDDでは本来、ドメイン分析を行い、境界づけられたコンテキストを発見するところから始めますが、これはウォーターフォール的な考え方です。実際には作りながら作りたいものが明らかになっていくことも多いでしょう。先に集約ルートから考え始めて、ワークフローが増えていく中で、同一のコンテキストを結合していく、という順番で進めると、小さく始めることができます。

参考に [dotnet/eShop](https://github.com/dotnet/eShop) の例を見てみましょう。 `src/Ordering.Domain/AggregatesModel` には `BuyerAggregate` と `OrderAggregate` があります。これは、購入者と決済方法に関するワークフローと、注文に関するワークフローは、1トランザクションで混ざることはないことを表しています。このように小さい集約を作ることで、ワークフローの関心の範囲に閉じたドメインモデルをつくることができます。

eShopではEntityFrameworkを使っている都合上、若干DBに引っ張られている部分はありますが、これは設計の匙加減の問題です。DBの表現方法とドメインモデルの表現方法が違うべきならばDBに依存しないビジネスロジックを書き、詳細としてDBとドメインモデルの変換を書けばいいだけです。

## オブジェクト指向でWlaschinのDDDを実践する

ここまでClean Architecture、EvansのDDD、WlaschinのDDDが出てきましたが、言っていることはそんなに変わりません。ビジネスロジックに集中せよ、詳細は依存性を逆転せよ、ということです。

1点、Wlaschinの主張で光るところは、モデル化にオブジェクト指向のツールを利用するのではなく、書類の変換という立場を取っているところです。この主張により、データストアの設計とドメインモデルの設計を切り離して考えやすくなりました。どうしてもクラス図から書き始めたら、そのままER図になっちゃいますからね。プログラミング言語の強みである型による制約によってワークフローを表すことで、データストアという詳細とは違う角度で、ロジックをモデルに落としこむことができます。

WlaschinのDDDは関数型言語でないと実践できないかといったら、そんなことはありません。単純な変換は普通に関数を使えばいいですし、依存は関数の代わりにインターフェイスを使えば良いです。代数的データ型がないことで和の型が表せないならば、エンティティに変換ルールのストラテジパターンを適用することができます。

## 気にしてはいけないことリスト

- すべてのインスタンスをDIコンテナで作ろうとするな。依存がインターフェイスになっていれば、テスタビリティも低くないし何の問題もないだろう
- ディレクトリ構成なんて気にしないで、今すぐリファクタしたいコードがある階層から始めよう
- Wlaschinに従ってすべてをパイプとしてうまく繋げようとか頑張らなくていい
